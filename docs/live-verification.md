# Контролируемая проверка парных передач

Этот документ описывает временную диагностику, включаемую по запросу, для заданий MRKT, Portals и Tonnel N2 → N1. Авторизация, подтверждение, точное сопоставление, ограничения площадок, политика запрета повторов и правила статусов не меняются. Автоматические тесты не являются доказательством реальной транзакции.

## Включение

Установите `LIVE_VERIFY=true` в `.env`. По умолчанию значение равно `false`; допустимы только `true` и `false`. Этот флаг сам по себе не разрешает реальную операцию.

Для первого прохода оставьте включёнными:

```dotenv
MRKT_DRY_RUN=true
PORTALS_DRY_RUN=true
MRKT_TRANSFER_DRY_RUN=true
PORTALS_TRANSFER_DRY_RUN=true
TONNEL_TRANSFER_DRY_RUN=true
LIVE_VERIFY=true
```

Перед контролируемым live-тестом отключите только флаг выбранной площадки. После изменения конфигурации перезапустите единственный экземпляр приложения. Локальный запуск:

```bash
.venv/bin/python -m app.main
```

Запуск через Compose:

```bash
docker compose up -d --build --force-recreate tg-auto-auth
docker compose logs -f --tail=100 tg-auto-auth
```

Не запускайте второй polling-процесс, не перезапускайте приложение во время операции и не удаляйте постоянный volume. После проверки верните dry-run и `LIVE_VERIFY=false`, затем перезапустите приложение в состоянии без активных заданий.

## Сохраняемые метаданные

События имеют префикс `LIVE_VERIFY`. Каждое событие содержит ID задания, рынок и ID аккаунтов N1/N2 в базе данных. В `result_metadata.live_verify` сохраняются ограниченный список событий, число вызовов мутаций и финальный результат проверки чтением.

Opaque ID представлены только типом в протоколе и коротким отпечатком SHA-256. Строковый и целочисленный ID дают разные отпечатки. Исходные идентификаторы остаются в памяти только для точного сравнения.

### Portals

- тип и отпечаток выбранного NFT ID;
- HTTP-статус CREATE и безопасные имена полей ответа;
- наличие и отпечаток offer ID, если он был возвращён;
- согласование чтением после HTTP 204 через N1 `/offers/placed`, N2 `/offers/nft/{nft_id}` и необязательный `/offers/received`;
- статус и доступные `created_at`, `updated_at`, `expires_at` точных кандидатов;
- появление, изменение статуса и исчезновение кандидата;
- точное совпадение offer ID, NFT ID, Decimal-суммы и доступного идентификатора отправителя перед ACCEPT;
- HTTP-статус ACCEPT и число вызовов CREATE/ACCEPT;
- финальные снимки владения N1/N2.

Неактивные кандидаты сохраняются в диагностике, но никогда не принимаются.

### MRKT

- тип и отпечаток точного gift ID;
- HTTP-статус и имена полей SALE;
- поля размещённого/неразмещённого подарка на стороне продавца;
- целое значение `salePrice` в nanoTON и доступный идентификатор продавца;
- результат `/saling/by-ids` и цена перед BUY;
- HTTP-статус и имена полей BUY;
- число SALE/BUY и финальные снимки владения N1/N2.

### Tonnel

- один CREATE и максимум один ACCEPT на точный подарок;
- безопасные временные отметки, вызывающий контекст/задание, тип и значение gift ID, сумма, HTTP-статус и поля `status`/`message` CREATE;
- разница множеств offer ID до/после и точная корреляция через N1 `getMyOffers` и N2 `getOffers`;
- `TONNEL_OFFER_ACCEPT_DELAY_MS=5000` между точным подтверждением оффера и единственным ACCEPT;
- проверка владения чтением до `TONNEL_OWNERSHIP_VERIFY_TIMEOUT_MS=15000`;
- `probe_count`, `first_probe_ms`, `confirmed_ms`, финальное владение и `accept_success_to_ownership_confirmed_ms`;
- защита транспортного уровня, запрещающая второй CREATE одного дочернего задания.

Если ACCEPT вернул `status="success"`, но владение не сошлось за 15 секунд, задание становится `AMBIGUOUS / OWNERSHIP_VERIFICATION_TIMEOUT`, а не обычным `FAILED`.

## Ограничения диагностических данных

Записываются только явно разрешённые имена и безопасные скалярные значения. Не записываются:

- исходные initData и authData;
- значения Authorization и cookies;
- Telegram session, ключ авторизации и пароли;
- полные тела HTTP-запросов и ответов;
- произвольные сообщения исключений с возможными секретами.

HTTP-статус сохраняется только при полученном ответе. Факт начала мутации без ответа не доказывает, дошёл ли запрос до сервера. Логи появляются сразу, а метаданные SQLite — при завершении задания. После аварии часть сведений может остаться только в логах; восстановление прерванного задания не повторяет запрос.

## Семантика финальной проверки

Проверки являются ограниченными и неатомарными снимками чтения. Согласование данных на стороне площадки может происходить с задержкой.

- `SUCCESS` — точный объект подтверждён у N1 и отсутствует у N2.
- `FAILED` — получен определённый отказ или подтверждено, что операция не выполнена.
- `AMBIGUOUS` — результат мутации или финальное владение нельзя доказать безопасно.
- `DRY_RUN` — мутация не отправлялась.

Никакая проверка чтением не повторяет мутацию и не превращает неоднозначный результат в успех без точного подтверждения.

## Контрольный live-чеклист

1. Используйте только два собственных аккаунта. Проверьте, что N1 — получатель/покупатель, а N2 — текущий владелец/продавец.
2. Выберите один или несколько недорогих объектов и проверьте баланс, комиссии, cooldown и ограничения в официальной Mini App.
3. Выполните dry-run. Ожидайте ноль событий мутации.
4. Отключите dry-run только у одной площадки и перезапустите приложение в состоянии без активных заданий.
5. Нажмите кнопку операции один раз. Не имитируйте обрыв сети во время funded-теста.
6. Проверьте типы и значения точных ID, сумму, количество мутаций и финальное владение по результатам чтения.
7. MRKT: убедитесь, что выполнены максимум один SALE и один BUY, а цена соответствует точной семантике nanoTON.
8. Portals: убедитесь, что выполнены максимум один CREATE и один ACCEPT; после HTTP 204 дождитесь завершения окна согласования.
9. Tonnel: убедитесь, что на каждый подарок есть ровно один CREATE и один ACCEPT, задержка перед ACCEPT не меньше 5000 мс, а проверка владения уложилась в 15000 мс либо вернула `AMBIGUOUS`.
10. Сравните русский итог бота с официальными Mini App и безопасными метаданными.
11. При `AMBIGUOUS`, расхождении снимков или недоступном идентификаторе остановитесь и выполните ручную сверку. Не запускайте повторное задание.
12. Верните безопасные значения dry-run.

## Доказательства перед штатным использованием

Для каждой площадки нужны: сохранение точного типа и значения идентификатора, правильная цена, максимум по одному вызову каждой мутации, подтверждённое владение и отсутствие скрытого повтора. Для batch дополнительно требуются атомарная защита повторного запуска, одно Telegram-сообщение прогресса и отдельное дочернее задание на каждый объект.

Один успешный контролируемый тест подтверждает конкретный контракт на момент проверки, но не гарантирует неизменность схемы, комиссий, ограничений или frontend bundles.
