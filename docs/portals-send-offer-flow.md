# Создание индивидуального оффера Portals

Исторический статический снимок от 2026-09-06. Публичный bundle `portal-market.com/assets/index-B1JQMpiB.js` был изучен без отправки оффера и принятия сделки.

## Подтверждённая последовательность

```text
пользовательская session Telegram
→ свежий @portals Main Mini App WebView
→ Authorization: tma <fresh initData>
→ GET /api/users/auth
→ N2: GET /api/nfts/owned?offset=0&limit=20
→ N1: POST /api/offers/
→ N1: GET /api/offers/placed
→ N2: GET /api/offers/nft/{nft_id}?limit=10
→ N2: POST /api/offers/{offer_id}/accept
```

Создание:

```http
POST https://portal-market.com/api/offers/
Authorization: tma <fresh Telegram initData>
Content-Type: application/json

{"offer":{"nft_id":"<opaque NFT id>","offer_price":"1.68"}}
```

`expiration_days` может находиться внутри `offer`; текущий интерфейс добавляет его только для вариантов 1 или 7 дней. Отсутствие поля означает бессрочный вариант интерфейса. ID получателя/продавца не передаётся: цель определяется opaque NFT ID.

Сумма — строка Decimal в TON, а не nanoTON. Интерфейс требует минимум `0.5` TON и применяет штатные проверки баланса и комиссии Portals.

Серверные этапы подготовки и завершения отсутствуют. Форма цены является локальным шагом подтверждения, а отправка формы выполняет один POST. `GET /api/offers/placed` показывает активные исходящие офферы; отмена использует `POST /api/offers/{offer_id}/cancel`, изменение — `PATCH /api/offers/{offer_id}`.

Контролируемый live-тест подтвердил успешный ответ `204 No Content`. Frontend считает любой успешный Axios 2xx успехом, обновляет запрос размещённых офферов и закрывает диалог. Тело ответа и offer ID отсутствуют.

Приложение не считает один HTTP 204 достаточным доказательством для ACCEPT. После него выполняется ограниченное согласование чтением через:

- N1 `GET /api/offers/placed`;
- N2 `GET /api/offers/nft/{nft_id}`;
- необязательный `GET /api/offers/received`.

Точный offer ID используется только когда найден один кандидат со статусом pending/active, точными типом и значением NFT ID, равной Decimal-суммой, допустимым окном `created_at` с допуском расхождения часов и совпадающим отправителем, если поле доступно. N1 `/offers/placed` является сильным свидетельством принадлежности N1; endpoint NFT на стороне N2 — обязательным подтверждением перед ACCEPT. Пустой `/offers/received` не блокирует точное совпадение.

Отменённые, истёкшие, отклонённые и другие неактивные кандидаты сохраняются в диагностике, но не принимаются. Несколько совпадений, отсутствие совпадений или неопределённые чтения дают `AMBIGUOUS`; CREATE не повторяется.

Dry-run проверяет NFT, сумму, свежую авторизацию и точное тело запроса без CREATE/ACCEPT. Резервация баланса, collateral, комиссии и итоговая допустимость на сервере могут быть подтверждены только контролируемым live-тестом.

Известные общие HTTP-статусы: 400, 401, 403, 404, 409, 429 и 5xx. Баланс, cooldown, блокировки, блокировка передачи, collateral, CAPTCHA, кошелёк и другие серверные ограничения не обходятся.
