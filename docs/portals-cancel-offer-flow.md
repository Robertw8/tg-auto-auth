# Отзыв размещённого оффера Portals

Исторический статический снимок от 2026-09-07. При проверке публичный frontend Portals ссылался на `https://portal-market.com/assets/index-CDQPuR1a.js`. Мутация отмены во время исследования не отправлялась.

## Последовательность официального frontend

```text
свежий @portals Mini App WebView
→ Authorization: tma <fresh Telegram initData>
→ GET /api/users/auth
→ GET /api/offers/placed?offset=0&limit=20
→ выбор одного точного оффера
→ локальное окно подтверждения удаления
→ POST /api/offers/{offer_id}/cancel
→ обновление placed-offer query
```

Запрос отмены:

```http
POST https://portal-market.com/api/offers/{offer_id}/cancel
Authorization: tma <fresh Telegram initData>
Content-Type: application/json
x-request-id: <client-generated UUID>

<no request body>
```

`offer_id` — opaque identifier из `GET /api/offers/placed`. Frontend вставляет его в path без изменения исходного типа. `nft_id` и сумма в запрос не включаются; приложение использует их только для повторной проверки выбранного оффера перед мутацией.

Выполняется ровно один запрос отмены. Отдельных мутаций подготовки или завершения нет. `onSuccess` принимает любой успешный Axios 2xx, показывает уведомление, сбрасывает кэш списка размещённых офферов и запускает обычный cooldown. Точные успешные HTTP-статус и тело ответа не использовались frontend и требуют отдельной контролируемой live-проверки.

Общий клиент Portals передаёт исходные Telegram initData в `Authorization: tma ...`. Token из `/users/auth` не подменяет этот заголовок; отдельная cookie-session для действия не обнаружена. Origin и Referer соответствуют контексту Web App на том же origin.

Ожидаемые ошибки общего API: HTTP 400, 401, 403, 404, 409, 429 и 5xx. Они не обходятся.

## Безопасность приложения

Бот показывает только офферы со статусом pending/active выбранного OWNER/N1 из `/offers/placed`. Пользователь выбирает точный opaque offer ID и подтверждает действие короткоживущим одноразовым callback.

Непосредственно перед отменой сервис повторно загружает `/offers/placed` и проверяет:

- точные тип и значение offer ID;
- точные тип и значение NFT ID;
- точную Decimal-сумму;
- статус, допускающий отмену;
- принадлежность выбранному аккаунту и пользователю управляющего бота.

POST отмены отправляется максимум один раз. После тайм-аута или неоднозначной сетевой ошибки выполняются только проверки чтением `/offers/placed`. Два последовательных успешных чтения без точного оффера считаются доказанным неактивным состоянием. Если оффер остаётся видимым или чтение не даёт однозначного результата, статус остаётся `AMBIGUOUS`, а отмена не повторяется.

Исходные initData, Authorization, cookies, Telegram sessions, ключи авторизации и полные тела API-ответов не выводятся и не логируются.
