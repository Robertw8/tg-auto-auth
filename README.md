# Подключение Telegram-аккаунтов через MTProto

Компактный управляющий Telegram-бот для подключения собственных Telegram-аккаунтов через штатную авторизацию MTProto и выполнения подтверждаемых операций с подарками в MRKT, Portals и Tonnel. Бот остаётся единственным пользовательским интерфейсом. Номер телефона, код входа и пароль 2FA вводятся только в Telegram Web App и никогда не отправляются сообщениями боту.

## Возможности

- авторизация нескольких Telegram-аккаунтов через Telethon;
- внутреннее хранение постоянных `.session` в `data/sessions/`;
- роли **Мой аккаунт** (`OWNER`, N1) и **Рабочий аккаунт** (`TARGET`, N2);
- сохранение активной пары N1/N2 после перезапуска;
- управление подключёнными аккаунтами и безопасное удаление с logout;
- русскоязычные интерфейсы бота и Web App;
- одиночные и парные операции MRKT;
- однокнопочная пакетная передача Portals и Tonnel;
- постоянные задания и состояние batch в SQLite;
- dry-run, защита от повторных callback и запрет автоматического повтора мутаций;
- история операций только для владельца управляющего бота.

## Требования

- Python 3.12 или новее;
- токен бота от [@BotFather](https://t.me/BotFather);
- Telegram API ID и API hash с [my.telegram.org](https://my.telegram.org);
- публичный HTTPS-адрес для Web App;
- SQLite и постоянное приватное хранилище для `data/`.

## Установка

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
cp .env.example .env
```

Заполните `.env`, затем запустите приложение:

```bash
python -m app.main
```

Один процесс одновременно запускает FastAPI Web App и polling aiogram. Несколько рабочих процессов или параллельных экземпляров polling для этого MVP не поддерживаются.

### Telegram и Web App

`BOT_TOKEN`, `TELEGRAM_API_ID` и `TELEGRAM_API_HASH` обязательны. Они не должны попадать в логи или репозиторий.

`WEBAPP_PUBLIC_URL` — внешний адрес формы авторизации. Он должен оканчиваться на `/auth`, не содержать query/fragment и использовать HTTPS. HTTP разрешён только для явно локального `localhost`. `WEB_HOST` и `WEB_PORT` задают локальный адрес встроенного FastAPI-сервера.

### Dry-run и live-режим

Все флаги dry-run по умолчанию равны `true`:

- `MRKT_DRY_RUN` — одиночное размещение MRKT;
- `PORTALS_DRY_RUN` — одиночное принятие Portals;
- `MRKT_TRANSFER_DRY_RUN` — парная передача MRKT;
- `PORTALS_TRANSFER_DRY_RUN` — пакетная передача Portals;
- `TONNEL_TRANSFER_DRY_RUN` — пакетная передача Tonnel.

Отключайте только один нужный флаг и только перед контролируемым live-тестом. Потерянный или неоднозначный ответ мутации не приводит к её повтору.

`LIVE_VERIFY=true` включает расширенную безопасную диагностику и дополнительные read-only проверки. Он сам по себе не отключает dry-run и не разрешает реальные операции.

### Portals

`PORTALS_AUTO_OFFER_AMOUNT=0.53` задаёт точную сумму каждого автоматического оффера Portals в TON. Значение обрабатывается через `Decimal`.

`MAX_PORTALS_CONCURRENT_JOBS=5` ограничивает число одновременно работающих дочерних заданий одного batch Portals. Допустимый диапазон — `1..5`.

### Tonnel

Текущая штатная стратегия:

```dotenv
TONNEL_TRANSFER_MODE=BUY_OFFER
TONNEL_API_ORIGIN=https://gifts.coffin.meme
TONNEL_AUTO_OFFER_AMOUNT=2
TONNEL_OFFER_ACCEPT_DELAY_MS=5000
TONNEL_OWNERSHIP_VERIFY_TIMEOUT_MS=15000
MAX_TONNEL_CONCURRENT_JOBS=5
```

`BUY_OFFER` работает с обычными подарками, переданными в `@GiftRelayer`. Telegram Business и публичное размещение для штатного Tonnel-потока не требуются. Tonnel отклоняет buy offer ниже `2` TON; поэтому `0.53` относится только к Portals и не является допустимой автоматической суммой Tonnel. С учётом комиссии создания оффера предварительно требуется не менее `2.01` TON на один подарок.

Batch один раз авторизует N1 и N2, держит оба контекста Tonnel только в памяти и передаёт их изолированным дочерним HTTP-заданиям без повторного открытия общих session-файлов Telethon.

После точной корреляции нового оффера выполняется подтверждённая live-тестом пауза `5000` мс, затем отправляется ровно один ACCEPT. Значение не следует уменьшать без отдельного контролируемого теста.

После ответа ACCEPT с `status="success"` бот до `15000` мс проверяет владение read-only запросами примерно раз в секунду. `SUCCESS` устанавливается только когда N1 владеет точным подарком, а N2 больше им не владеет. При тайм-ауте задание становится `AMBIGUOUS`, а ACCEPT не повторяется.

`MAX_TONNEL_CONCURRENT_JOBS` ограничивает параллельность независимых подарков диапазоном `1..5`.

`MARKET_SALE` сохранён только как явно выбираемая резервная публичная стратегия. `DIRECT_RECIPIENT` относится к отдельному исторически исследованному потоку Telegram Business и не является штатным режимом.

## Настройка BotFather

1. Разверните FastAPI за стабильным HTTPS-доменом с действительным сертификатом.
2. В `@BotFather` выполните `/setdomain`, выберите управляющего бота и укажите домен `WEBAPP_PUBLIC_URL`.
3. Запишите полный адрес с `/auth` в `WEBAPP_PUBLIC_URL` и перезапустите приложение.
4. Отдельная menu-button Web App не требуется: бот создаёт inline-кнопку `web_app` для каждой короткоживущей попытки входа.

Для локальной проверки на телефоне опубликуйте `127.0.0.1:8000` через доверенный HTTPS-туннель. Никогда не публикуйте `.env`, `data/` или корень проекта.

## Авторизация аккаунта

1. Пользователь отправляет `/start` и нажимает **Добавить аккаунт**.
2. Бот создаёт пятиминутную попытку и случайный одноразовый launch token, связанный с Telegram ID пользователя управляющего бота.
3. Web App получает token через URL fragment, поэтому он не попадает в access-логи и Referer.
4. Сервер проверяет подпись и свежесть Telegram `initData`, владельца, срок действия, same-origin и CSRF.
5. Пользователь вводит телефон. `send_code_request()` вызывается ровно один раз для попытки.
6. Код входа вводится в Web App. Для `sign_in()` используются те же нормализованный телефон, `phone_code_hash`, Telethon-клиент и временная session.
7. При необходимости пароль 2FA вводится отдельной формой того же Web App.
8. После `get_me()` метаданные сохраняются в SQLite, а внутренняя session — в `data/sessions/`.
9. `/accounts` и **Мои аккаунты** показывают подключение после перезапуска.
10. Удаление аккаунта сначала пытается выполнить logout, затем удаляет локальную session и запись SQLite.

OTP, пароль 2FA, raw `phone_code_hash`, auth key, StringSession, tdata, cookie и содержимое session никогда не возвращаются пользователю, не сохраняются в SQLite и не логируются.

## Роли аккаунтов

- **Мой аккаунт** — постоянный `OWNER`/N1: получает подарки, совершает покупки и отправляет офферы.
- **Рабочий аккаунт** — `TARGET`/N2: владеет исходными подарками, размещает их или принимает офферы.

Активная пара N1/N2 принадлежит одному пользователю управляющего бота и сохраняется в SQLite. Повторное подключение той же Telegram-личности обновляет роль и внутреннюю session без экспорта credentials.

## Главное меню

`/start` открывает русское меню:

```text
Добавить аккаунт
Мои аккаунты
MRKT
Portals
Tonnel
История операций
Помощь
```

Старые callback имеют короткий срок действия и отклоняются после смены шага. Телефоны маскируются. История ограничена текущим пользователем и не показывает auth-данные, initData, cookies или полные ответы площадок.

## MRKT

Одиночный MRKT-поток загружает Storage, использует точный opaque `gift.id`, принимает цену TON максимум с двумя десятичными знаками и переводит её в integer nanoTON через `Decimal`. Только явное подтверждение может отправить один `POST /api/v1/gifts/sale`.

Парная операция N2 → N1 использует один SALE и максимум один BUY. Штатный `FAST_CONFIRMED` начинает подготовленный BUY после определённо успешного SALE. Дополнительные режимы `LISTED_TRIGGERED` и `SPECULATIVE` включаются только явно и описаны в исследовательской документации. Ни один режим не повторяет мутацию после тайм-аута или неоднозначного результата.

MRKT использует публичную продажу, поэтому остаётся риск покупки другим участником между SALE и BUY. Финальные read-only проверки различают получение N1, сохранение у N2 и неопределённое внешнее владение.

## Однокнопочная передача Portals

Кнопка **Portals** использует активную пару N1/N2 и загружает все подходящие NFT N2. Для каждого NFT создаётся отдельное постоянное задание `transfer_jobs`, а все дочерние задания объединяются одним batch.

Для каждого NFT:

1. N1 создаёт ровно один оффер на `PORTALS_AUTO_OFFER_AMOUNT`.
2. После HTTP 204 приложение не ожидает ID в теле ответа, а восстанавливает точный `offer_id` через ограниченное согласование чтением.
3. Сопоставляются точные тип и значение NFT ID, точная Decimal-сумма, активный статус и доступные поля отправителя.
4. N1 `/offers/placed` и N2 `/offers/nft/{nft_id}` должны подтвердить один и тот же opaque offer ID.
5. N2 отправляет максимум один ACCEPT.
6. При неоднозначности повтор CREATE или ACCEPT запрещён.

`/offers/received` используется только как дополнительное свидетельство и не является обязательным условием.

## Однокнопочная пакетная передача Tonnel

Кнопка **Tonnel** автоматически загружает все подходящие обычные подарки N2. Ручной выбор подарка и ручной ввод цены в штатном batch-потоке отсутствуют.

Один логический запуск создаёт:

- одну постоянную запись batch;
- одно дочернее задание на каждый точный подарок;
- один CREATE и максимум один ACCEPT на подарок;
- одно Telegram-сообщение прогресса, которое редактируется до финального результата.

Атомарная резервация в SQLite блокирует второй batch для той же пары N1/N2. Повторное нажатие отвечает **Передача уже выполняется.** и останавливается до загрузки инвентаря, создания дочерних заданий и обращения к площадке. Дополнительная защита транспортного уровня запрещает повторный вход одного дочернего задания в CREATE.

Исторические офферы исключаются сравнением множества offer ID до и после CREATE. Новый оффер должен одновременно присутствовать в N1 `getMyOffers` и N2 `getOffers` с точными gift ID, суммой и доступными данными покупателя и продавца.

Итоговые состояния взаимно исключаются:

- `SUCCESS` → **Успешно**;
- `DRY_RUN` → **Тестовый запуск**;
- `FAILED` → **Ошибка**;
- `AMBIGUOUS` → **Требует проверки**.

## История и восстановление после перезапуска

SQLite хранит безопасные параметры заданий, фазу, статус и ограниченные диагностические метаданные. Секреты и полные тела ответов API не сохраняются.

При старте приложение:

- валидирует конфигурацию;
- инициализирует SQLite;
- очищает незарегистрированные session-файлы;
- переводит прерванные мутационные задания в безопасное `AMBIGUOUS`;
- восстанавливает batch-состояние без автоматического повтора операций;
- запускает FastAPI и aiogram polling.

## Диагностика

- **Код Telegram не пришёл:** найдите безопасный лог попытки, delivery type и RPC exception. Не запрашивайте новый код многократно и соблюдайте `FloodWait`.
- **Аккаунт отозван:** переподключите его через Web App; не копируйте старый session-файл.
- **Batch уже выполняется:** дождитесь завершения активного batch. Не запускайте второй процесс polling.
- **Требуется проверка:** вручную проверьте обе стороны в официальной Mini App. Не повторяйте операцию, пока состояние не согласовано.
- **Tonnel ACCEPT успешен, но владение не обновилось:** дождитесь 15-секундного read-only окна. При тайм-ауте задание останется `AMBIGUOUS`, без повторного ACCEPT.
- **HTTP 429 или ограничение площадки:** соблюдайте cooldown; приложение не обходит rate limit, CAPTCHA и другие ограничения.

## Производственная эксплуатация

- Запускайте ровно один контролируемый процесс и один polling-процесс aiogram.
- Публикуйте только `/auth`, `/api/auth/*`, `/static/*` и при необходимости `/healthz`.
- Храните `.env`, SQLite и session-файлы в зашифрованном приватном хранилище.
- Резервируйте `data/app.db` и `data/sessions/` вместе.
- Ограничьте доступ к логам: даже безопасные fingerprints и DB IDs являются метаданными.
- Разрешайте graceful shutdown завершить disconnect Telethon-клиентов.
- Перед расширением аудитории добавьте allowlist/enrollment, проверенные backup/restore и revocation-процедуры, pinning зависимостей, мониторинг и сканирование уязвимостей.
- Повторно проверяйте content-hashed frontend contracts MRKT, Portals и Tonnel после обновлений площадок.

## Гарантии безопасности

- штатная Telegram/Telethon-авторизация без обхода 2FA, flood limit или security checks;
- OTP и пароль 2FA не проходят через сообщения бота;
- session, StringSession, tdata, auth key, initData, Authorization и cookies не экспортируются;
- мутации не повторяются автоматически после неопределённого результата;
- точные типы и значения идентификаторов, а также Decimal-суммы проверяются перед операцией;
- stale/replayed callback отклоняются;
- batch и child jobs резервируются атомарно;
- CAPTCHA, cooldown, password, wallet, marketplace и anti-bot ограничения не обходятся.
